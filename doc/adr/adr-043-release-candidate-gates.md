# ADR-043: Executable Release-Candidate Gates

**Tags:** `release`, `golden`, `dogfood`, `provenance`, `security`

---

## Status

Accepted — 2026-07-14

## Context

Passing unit tests does not prove that distributed archives can be installed,
that an existing binary can be upgraded, or that real committed configuration
still produces stable output. The v1 candidate also needs verifiable release
identity and a documented security boundary.

## Decision

- Treat release-candidate acceptance as a dedicated pull-request workflow.
- Freeze a high-signal generated path set in a checked-in golden file.
- Generate goboot's committed configuration twice and compare every output
  digest.
- Replace a baseline installation with the candidate before smoke testing.
- Build snapshot archives and verify checksums, extraction, execution, and SBOMs.
- Sign release binaries and checksums with keyless Sigstore identities and add
  GitHub build-provenance attestations.
- Keep measured performance limits and the threat model explicit in versioned
  documentation.

## Consequences

- Output-shape changes become visible review events.
- Release packaging failures are caught before a tag is created.
- The repository exercises its own public configuration and regeneration path.
- Tag releases require OIDC, attestation, Syft, and Cosign availability.
- The workflow is intentionally slower than ordinary unit tests but remains
  isolated as one named release-candidate gate.

## Alternatives considered

### Depend on unit tests and GoReleaser configuration checks

Configuration checks do not extract, execute, upgrade, or verify release assets.
They also do not exercise the real committed goboot configuration.

### Store a golden copy of every generated byte

That would duplicate a large generated repository and make intentional template
maintenance noisy. The checked-in path contract plus full repeat-generation
digest comparison catches shape drift and nondeterminism with less duplication.

### Store a long-lived signing key in Actions secrets

Keyless OIDC signing avoids key rotation and secret-exfiltration risk while
binding signatures to the release workflow identity.
