# Safe Regeneration

Goboot generates each requested project in an isolated staging directory before
it inspects or changes the real target. It then creates a deterministic plan from
the staged output, the current project, and the previous ownership manifest.

## Ownership manifest

After a successful run, goboot writes `.goboot-manifest.yml` in the generated
project. The manifest records:

- manifest schema version
- goboot version
- active template profile
- enabled service IDs
- each goboot-owned file path
- the file's SHA-256 digest and permission mode

Commit the manifest with the generated project. It is the evidence goboot uses
to distinguish unchanged generated output from subsequent user edits.

Deleting or corrupting the manifest does not make goboot overwrite files. Under
the default policy, existing collisions without valid ownership evidence are
reported as conflicts.

## Policies

Select the default in the root config:

```yaml
regenerationPolicy: managed
```

Override it for one run when necessary:

```bash
goboot --config ./configs/goboot.yml --regeneration-policy preserve
```

| Policy | Existing unchanged owned file | User-modified or unowned collision | Stale owned file |
| ------ | ----------------------------- | ---------------------------------- | ---------------- |
| `managed` | Update | Conflict | Delete when unchanged; conflict when modified |
| `replace` | Update | Replace | Delete, including modified stale output |
| `preserve` | Keep | Keep and relinquish ownership | Keep and relinquish ownership |

`managed` is the default. Use `replace` only when the generated definition is
intentionally authoritative. Goboot does not claim a generic `merge` policy:
safe merge semantics depend on the file format and need a dedicated owner.

File/directory type collisions are always conflicts. Symbolic links and special
files are rejected in generation trees because following or recreating them
would weaken the project-root safety boundary.

## Dry runs

Preview a complete plan without creating or changing the target project:

```bash
goboot --config ./configs/goboot.yml --dry-run
```

Plan actions are `CREATE`, `UPDATE`, `DELETE`, `PRESERVE`, `CONFLICT`, and
`UNCHANGED`. A summary count follows the path list. Conflicts produce a non-zero
result after the plan is printed.

Dry runs still execute template rendering and, unless disabled, `go mod tidy`
inside the temporary staging tree. This keeps the preview faithful to the final
generated bytes while leaving the configured target untouched.

## Transaction lifecycle

For a successful non-dry run, goboot:

1. generates and validates the complete staged project
2. computes hashes, modes, ownership, and conflicts
3. creates a candidate beside the target so renames stay on one filesystem
4. copies existing unowned or preserved files into the candidate
5. applies generated creates, updates, and deletions to the candidate
6. writes the new ownership manifest
7. moves the current project to a temporary backup and renames the candidate
   into place
8. restores the backup if the commit rename fails, then removes successful
   transaction artifacts

The real project is not edited file by file. A portable two-rename swap has a
brief interval between moving the old tree and installing the candidate, but the
old tree remains available for rollback throughout that interval.

If planning, candidate creation, copying, or rendering fails, the target project
is unchanged and temporary generation data is removed.
